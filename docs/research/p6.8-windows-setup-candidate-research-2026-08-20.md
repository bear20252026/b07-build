# P6.8：Windows Setup.exe 候选包

**状态：** 实现中，Windows x64 优先。

## 目标与边界

本阶段将 P6.6 的 `awo-native-host-helper` Windows x64 候选二进制包装为一个 **每用户、可卸载、手动运行的 Setup.exe**。它采用本机已安装并经验证的 Inno Setup 6.7.3 命令行编译器；构建过程可复现，且 GitHub Actions 会对候选 ZIP 和 Setup.exe 分别生成 SLSA provenance。

> Setup.exe 是安装容器，不是信任提升。它不会让原生 helper 自动成为 trusted bridge、不会激活构件、更不会授予执行权限。

| 层次 | 职责 | 本阶段允许 | 明确禁止 |
|---|---|---|---|
| P6.6 helper candidate | 固定的只读 helper 二进制、SBOM 与摘要 | 作为安装器唯一 payload | 更改其 `unsigned-candidate` 状态 |
| Inno Setup definition | 每用户复制 helper 并生成卸载器 | 复制到 `%LOCALAPPDATA%\\Programs\\AI Work OS\\Native Host Helper` | 自动启动、服务/协议/环境变量/注册表、系统提权 |
| Setup manifest + verifier | 声明安装器、源候选摘要和策略 | 校验 PE 头、SHA-256、文件 allowlist 和禁止字段 | 运行安装器、卸载、签名、导入证书 |
| GitHub provenance workflow | 托管 runner 构建并绑定来源 | 上传工件、对 ZIP 与 Setup.exe 分别生成 attestation | 接触私钥、正式发布、自动安装/信任 |

## Inno Setup 设计

安装定义 `installers/windows/awo-native-host-helper.iss` 仅有 `[Setup]` 和 `[Files]` 两个功能段。它固定 `PrivilegesRequired=lowest`、`ArchitecturesAllowed=x64compatible`、`ArchitecturesInstallIn64BitMode=x64compatible`、`DisableProgramGroupPage=yes`，并将 helper 写入每用户目录。由于没有执行段、注册表段、代码段、任务段或图标段，安装和卸载不会启动 helper 或其他程序。

Inno Setup 官方文档确认，`ISCC.exe` 可作为命令行编译器，且其成功/失败由退出码表示；`[Files]` 段用于定义复制文件；而执行段是可选的、会在安装后启动程序。本项目刻意没有使用执行段。[1] [2] [3]

输出文件名刻意使用 `AI-Work-OS-Native-Host-Helper-<version>-Installer.exe`，而不是 `setup.exe`。Inno 官方明确警告不要使用 `setup.exe` 作为输出文件名，因为 Windows 应用兼容层会以不安全方式加载额外 DLL，从而存在 DLL 劫持风险。[2]

## 实机验证

Windows 11 x64 / PowerShell 5.1 上发现并使用：

| 工具 | 发现版本 | 验证结果 |
|---|---:|---|
| Inno Setup | 6.7.3 | `ISCC.exe` 实际成功编译候选安装器 |
| NSIS | 3.12 | 已发现但未采用；本阶段统一采用 Inno Setup |
| Setup candidate | `0.1.0-dev.8` | 生成 `AI-Work-OS-Native-Host-Helper-0.1.0-dev.8-Installer.exe`，大小 2,194,566 字节 |
| Static verifier | P6.8 verifier | 返回 `valid: true`、`signingStatus: unsigned-candidate`、`canManualInstall: true`、所有自动信任/激活/发布字段为 `false` |

此验证仅构建和静态校验安装器，**没有运行 Setup.exe**，因此没有向设备安装 helper 或创建卸载登记。

## 构建与验证

在 Windows 设备执行以下命令即可生成新的候选安装包；版本号应当是新的，输出目录不允许覆盖已有候选：

```powershell
.\scripts\windows\build-setup-candidate.ps1 -Version 0.1.0-dev.8
.\scripts\windows\VERIFY-SETUP-CANDIDATE.ps1 `
  -SetupDirectory .\artifacts\windows-x64\setup
```

GitHub Actions 运行后，下载 Setup.exe 后应使用精确仓库与签发工作流核验：

```bash
gh attestation verify AI-Work-OS-Native-Host-Helper-0.1.0-dev.8-Installer.exe \
  --repo bear20252026/b07-build \
  --signer-workflow bear20252026/b07-build/.github/workflows/windows-native-host-provenance.yml
```

GitHub 官方文档指出，构建来源证明应当用于二进制工件并通过 CLI 验证；它建立工件与仓库、提交、工作流的可验证关联，但不能替代安全审查或公开 CA 代码签名。[4] [5]

## 不变的安全结论

1. Setup.exe 与其 payload 都保持 `unsigned-candidate`，直到未来独立的真实 Authenticode 签名流程。
2. 自签名开发副本仍仅适用于本机学习验证；不用于公开信任，也不自动签署 Setup.exe。
3. GitHub SLSA provenance 证明构建来源和完整性，不证明软件无缺陷、身份经 CA 认证或获 Windows SmartScreen 信任。
4. 安装器可以由用户手动运行，但构建器、验证器、GitHub Actions 与 runtime 均不会自动运行安装器或 helper。
5. 安装行为不注册 native bridge、不提升 `ComponentManagementAuthority`、不安装/激活插件、不创建服务或自启动项。
