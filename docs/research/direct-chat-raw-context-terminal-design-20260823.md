# 直接聊天、原始网页上下文、附件与本地终端设计

## 数据流

```text
用户显式选择文件 / 点亮联网检索 / 提交终端命令
    -> Workbench 临时内容准备（不写入旧 Gateway）
    -> Tauri 原生命令（Provider HTTPS/SSE、Web 检索、当前用户终端）
    -> 会话账本保存可见消息、原始上下文状态、来源、工具活动和输出
    -> 同一会话下次发送时按顺序重放到 Provider
```

| 数据类型 | 保存与传递 | 不静默缩减原则 |
|---|---|---|
| 用户/助手历史 | 同一对话本地账本；按用户选择模型的请求上限传入 Provider | 提高公共上限至 1,000,000 UTF-8 字符；如模型自身拒绝，显示供应商错误，不篡改记录。 |
| 文本附件 | 用户明确发送时读取；名称、MIME、完整文本和纳入状态进入当前用户消息的 Provider 上下文 | 超出本轮上下文或无法作为文本读取时保留可见状态与原因，不称“已发送”。二进制文件不伪造文本。 |
| 网页 | 检索得到的标题、URL、原始可读正文作为同一轮 Provider 上下文，用户可展开查看来源 | 以所选模型可接受上限为预算；每个未装入来源显示原因，而不是把所有来源压成未标识摘要。 |
| 终端 | 用户在终端工作面输入命令；原生进程以当前 Windows 用户权限执行；输出和退出码记录为本地活动 | 不使用管理员提权或后台常驻服务；常规命令不经过固定模板伪装成“计划”。危险破坏性/管理员/外部副作用命令须最后一次确认。 |

## 对用户反馈的根因

当前首页路径用 `directConversations.send()`，但是只交给它纯文本 `goal`，导致附件的 `File` 对象从未进入直接 Provider 请求。唯一现有的附件编码路径属于已退役的 loopback 任务客户端，因而首页看上去“已添加附件”，实际模型没有文件内容。

当前会话账本将消息限制为 200 条、每条 24,000 字符、请求 48 条/72,000 字符。这不是第三方 Provider 的普遍必要限制，会造成长会话被前端主动省略。修复以 1,000,000 字符为统一客户端预算并保留会话完整记录；供应商的真实上下文窗口仍由其服务端最终决定。

## 搜索适配策略

独立检索适配器不得把单个 Exa MCP 调用视为唯一来源。适配层应提供：可用性探测、初始化/认证错误、请求执行中、响应解析、原始网页抓取、来源逐项状态和模型装入范围。MCP 远程服务需遵守其初始化和会话协商流程；无法检索时要显示可见错误与后续可配置 Provider，而非保留一个看似启用但无效果的按钮。

参考资料与许可边界见 `last30days-openworker-atomcode-integration-review-20260823.md`。

## 本地预览核验

在隔离的 Workbench 本地预览中，未配置 Provider 且未发送消息时，联网检索按钮显示中性“联网检索”状态；点击后立即变为明显的系统蓝“联网检索已开启”，并带状态提示，页面没有执行搜索请求。该状态仅表示“下一次发送将启用检索”，实际搜索执行、原始网页抓取与 Provider 传递仍只在用户提交消息之后发生。

## 验证结果

本轮新增的文本附件上下文测试、历史消息 payload 测试、原始网页 MCP JSON/SSE 解析测试、UTF-8 截断测试与终端命令确认测试均通过。全仓 `npm test` 为 **312/312** 通过；TypeScript、Workbench 生产构建、Rust `cargo test`、`cargo check` 与差异空白检查通过。

独立搜索适配器现先进行远程 MCP 初始化和 initialized 通知，再调用 Exa `web_search_exa` 工具；返回 URL 后会逐页读取可访问网页的可读文本，并把标题、URL 和原文一同写入本轮 Provider 上下文。无法抓取的来源会保留在搜索活动中，但不会谎称模型已收到该页面全文。

终端窗口已从固定模板计划改为用户显式输入的当前用户权限命令执行：可查看 stdout/stderr、退出码与停止状态。尚待 Windows 安装版中实际运行普通命令、取消命令、搜索和真实 Provider 附件发送的最终人工核验；浏览器预览没有 Tauri 原生命令，因此不能替代此项验证。

## 多格式附件与自动 TXT 上下文

聊天附件不再只保留名称描述符。文本和代码文件通过浏览器 `File.text()` 读取后作为本轮 Provider 正文；PNG、JPEG、WebP 和 GIF 则在用户明确发送时编码为标准 OpenAI-compatible `image_url` 或 Anthropic `image` 内容块。PDF 使用原生文本提取；DOCX/ODT、XLSX/ODS、PPTX/ODP 从其 Open XML / ZIP 文本载荷中提取可读内容；ZIP 会传入文件目录。对扫描型 PDF、旧式 `.doc/.xls/.ppt`、RAR/7z、视频/音频或提取失败的附件，界面保留“未传递”的明确原因，不会错误标记为“已被模型读取”。

当输入超过 12,000 字符时，会话会生成带唯一名称的虚拟 TXT 上下文记录（不丢弃原始问题）；完整 TXT 正文会同当前消息保存并在下一轮继续作为会话上下文传给 Provider。总请求仍按 1,000,000 UTF-8 字符预算校验；如果所选供应商本身的窗口更小或拒绝请求，供应商错误会直接呈现，应用不会修改本地历史来假装成功。
