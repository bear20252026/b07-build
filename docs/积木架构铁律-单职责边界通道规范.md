# "积木架构"铁律 · 模块/依赖规范（单职责 + 边界 + 通道化）

> 约束来源：用户明确要求 —— **一个文件只有一个作用；一组文件只发挥一类作用；不同功能外边界清晰；之间通过渠道(channel/port)交流；改一行不颠覆整个系统；像搭积木一样拼系统。**
> 作用范围：与《AI工作操作系统-融合型实施方案》配套；本规范是该方案的内核纪律，优先于任何"顺手放一起"的写法。

## 一、三大铁律（不可违背）

1. **单职责定律**：一个文件只承担一种作用。文件内不得混入跨职责逻辑（例：一个文件既解析请求又写数据库，即违规）。
2. **边界定律**：一个目录/一个包只发挥一类作用。功能外边界必须清晰——UI 不碰 DB、Agent 引擎不碰窗口、sidecar 不碰 shell 业务。
3. **通道定律**：模块之间**不直接 import/调用对方内部实现**，只通过**唯一渠道(port/通道)**交流。依赖方向单向（外层→内层，语言内模块→协议边界），替换实现只换实现、不换协议。

**验收判据**：任意改一行代码 / 替换一个实现，不需要动其它模块的文件 = 达标。

## 二、积木的最小单元：端口(port) + 适配器(adapter)

每个积木 = **一个接口(port，面向通道，稳定) + 一个实现(adapter，可整体替换)**。消费方只依赖 port，不依赖 adapter。

```
[消费者] --(只依赖 port)--> [port 接口] <--(adapter 实现 reinvent)---- [实现A / 实现B]
                                        |
                                   [唯一通道: 事件/JSON-RPC/接口调用]
```

规则：同类型可替换实现(如 Provider A/B、OCR A/B)必须共用同一 port；新增实现=新增 adapter 文件，不改消费方。

## 三、三语言各自的"一文件一职责"模块契约（对应任务 #2）

> 目录名即"一类作用"；文件粒度到"一种作用"。以下用 `用途:一个文件 = 一作用` 标注。

### 3.1 Rust（控制面边界层）——每 crate 一类作用，禁业务逻辑

```
crates/
  control-plane/        # 作用=壳生命周期总调度；一个文件=一种调度事件处理
  window-manager/       # 窗口创建/拖拽/托盘；不碰业务
  life-cycle/           # 启动顺序/退出清理/崩溃恢复；不碰业务
  process-supervisor/   # 拉起 Python sidecar / 随父自杀 / 日志；不写业务
  security-vault/       # 密钥存储/解密；不碰业务
  capability-token/     # 短周期 token 签发/校验
  proxy-gateway/        # 进程内 axum 代理：模型路由/故障转移/多key轮换
  stt-native/           # 离线语音转写(ocw-stt 式)；只管"转成文本"
File 铁律：ts.rs 只管类型；service.rs 只管服务实现；error.rs 只管错误码；
          一个文件不得既做"代理路由"又做"凭证解密"。
```

### 3.2 TypeScript（产品与 Agent 生态）——每 package 一类作用，domain 与 UI 分包

```
packages/
  protocol/            # 唯一事实源：TaskEvent/CapabilityPolicy/ModelCapability JSON Schema + TS 类型（只放"类型定义"，不放逻辑）
  agent-runtime/       # Planner / DAG 执行器 / 审批编排（只管执行语义，不碰窗口）
  provider-sdk/        # ModelDriver 端口 + adapter（每 provider 一个 adapter 文件）
  mcp-host/            # MCP 客户端/服务器注册(只管 MCP 协议)
  plugin-sdk/          # 插件加载/权限声明(只管插件边界)
  artifact-sdk/        # 产物元数据/可编辑表示(不碰文件 IO 实现)
  ui-kit/              # 设计 tokens/命令面板/产物卡片(纯展示，不调业务)
File 铁律：types.ts 只放类型；adapter-xxx.ts 只实现该 xxxx 适配；bus.ts 只管事件总线转发；
          组件(x.tsx)只渲染，不直接调 provider。
```

### 3.3 Python（重计算 sidecar）——每 worker 一类作用，只做"输入→重算→输出"

```
sidecars/
  document-worker/     # PDF/DOCX/PPTX 解析+OCR：只管"文档→结构化文本/元数据"
  retrieval-worker/    # Embedding + RAG：只管"文本→向量→检索"
  speech-worker/       # STT/TTS：只管"音频→文本 / 文本→音频"
File 铁律：app.py 只建 FastAPI 路由;  processor.py 只做处理; auth.py 只管 token;
          一个文件不得既做"解析PDF"又做"语音转写"。
```

## 四、渠道(channel)清单与依赖方向规则（对应任务 #3）

> 所有跨模块/跨语言通信必须走下列**唯一渠道**；任何"直线 import 对方内部"均为违规。

| # | 渠道 | 通信双方 | 协议 | 归属 |
|---|---|---|---|---|
| C1 | `tauri invoke` + Event | 前端(React) ↔ Rust 控制面(系统能力) | Tauri 原生 | 窗口/权限/STT/更新/崩溃 |
| C2 | HTTP/SSE + WS | 前端/TS编排 ↔ Python sidecar(业务/重算) | JSON-RPC/EventStream | `127.0.0.1`+token |
| C3 | JSON-RPC 事件 | TS编排 → Rust(写事件日志/权限) | 事件协议 | 可审计/可恢复 |
| C4 | QoS 通道(port 抽象) | TS 模块间/语言内模块间 | 接口调用(port) | 只依赖接口不依赖实现 |
| C5 | 进程内代理 | 外部 CLI/Provider → Rust 代理 | HTTP(base_url 指向本地) | 路由/故障转移 |
| C6 | 事件订阅总线 | UI ↔ 领域事件 | EventStream | UI 只订阅不改状态 |

### 依赖方向（单向，禁止反向）
```
React/UI ──C1/C6──▶ Rust 控制面 ──C2──▶ Python sidecar
     │                  ▲
     └────C4(port)──────┘ (TS 领域包只依赖 protocol port)
Python │            │ 不反向
Rust  │ 不反依赖 UI / 不反依赖业务
```
**铁律**：UI 不得直连 DB；Agent 引擎不得直连窗口；Python 不得反向控制 Rust shell；Rust 不得写业务逻辑。渠道是唯一的交界，其余一律禁止跨层。

## 五、"改一行不颠覆"的成熟度判定

| 场景 | 达标做法 | 反例(违规) |
|---|---|---|
| 换模型 | 新增 provider adapter → 路由选它 | 改 Agent loop 硬编码模型逻辑 |
| 换 OCR 引擎 | 换 document-worker 内 adapter，port 不变 | 在 React 里改 OCR 调用 |
| 换数据库 | 换 Rust 数据层实现，port(事件日志接口)不变 | UI 直接拼 SQL |
| 加渠道(如 Slack) | 新增"渠道 adapter"接 C6 事件总线 | 改每个功能页加渠道分支 |
